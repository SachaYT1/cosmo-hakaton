# Отчёт: двухэтапный мониторинг природных пожаров по данным ДЗЗ

КосмоХакатон 2026, Красноярск. Команда сдаёт: модуль детекции активного горения (AF),
модуль картирования гарей и степени поражения (BS), submission.csv,
информационно-аналитический сервис, репозиторий.

## 1. Задача и протокол оценки

По чипам VIIRS (256×256 @ 375 м, каналы I1–I5) требуется выделить пиксели природного
горения, отделив их от техногенных термоаномалий; по парам снимков Sentinel-2 «до/после»
(512×512 @ 20 м) — контур гари и степень поражения (1/2/3). Метрика:

```
Score = 0.35·F1_af + 0.35·IoU_burn + 0.30·mIoU_sev
```

все компоненты — микро-усреднение по общему пулу пикселей. Ответ — единый submission.csv
в RLE. Оценка ведётся на private-выборке, разнесённой с train и по территории, и по времени
(весь 2025 год) — поэтому весь контроль качества у нас построен на кросс-валидации
с группировкой, исключающей утечки (раздел 4).

## 3. Baseline и отправная точка

Официальный baseline и скрипт метрики в выданном архиве **отсутствовали** (вопрос задан
организаторам). Поэтому отправная точка написана нами по тексту постановки:

- `firemon/rle.py` — RLE-кодек (нумерация с 1, построчно; round-trip проверен на случайных
  масках), `firemon/metric.py` — Score с микро-усреднением (нулевой знаменатель = 1);
- **AF-baseline (правило)**: день I4 > 330 K; ночь I4 > 317 K и превышение фона 15×15 на 3 K.
  F1 = 0.867 (день 0.897, ночь 0.534);
- **BS-baseline (правило)**: медианный dNBR 3×3, глобальный порог контура 0.12, минимальная
  компонента 200 px, пороги степеней по покрову. IoU_burn = 0.434, mIoU_sev = 0.462.

Ограничения этой отправной точки, из которых выросли гипотезы: фиксированный порог не
работает ночью (→ обучаемый классификатор на контекстных признаках); один порог dNBR
на разнородном покрове даёт ложные контуры на пашне (→ пороги по покрову + пространственная
модель контура); техногенные источники неотличимы по одному порогу (→ контекст снимка).

## 4. Эксперименты и сравнения

Условия одинаковы для всех сравнений: seed 42, единая метрика (наша реализация Score),
CV с группировкой: AF — 3 фолда по дате съёмки (чипы одного пролёта не разносятся
по фолдам), BS — по чипу-пожару. Все числа out-of-fold.

**Модуль AF: правило → LightGBM.** Признаки: I1–I5, I4−I5, зенитные углы, флаг дня,
превышение пикселя над локальным средним и z-score в окнах 7/15/31 px (для I4 и I4−I5),
локальные максимумы, покров, рельеф, метео, NDVI. Классификатор — LightGBM по кандидатам,
рабочий порог 0.44 выбран на OOF-предсказаниях 2019–2023 годов.

| Модель | F1 (все) | день | ночь | под смесь теста |
|---|---|---|---|---|
| Правило | 0.867 | 0.897 | 0.534 | 0.855 |
| **LightGBM + NOAA weak labels** | **0.953** | — | — | — |

Абляции и проверки устойчивости: раздельные пороги день/ночь выигрыша не дают (оба
сходятся к 0.43, честная CV — 0.952); F1 стабилен в диапазоне порогов 0.25–0.50 (±0.002) —
рабочая точка не хрупкая; bootstrap 95 % ДИ: день [0.946, 0.959], ночь [0.945, 0.972];
по спутникам: SNPP 0.950, NOAA-20 0.958, NOAA-21 0.957. Главные признаки — I4 и превышение
I4−I5 над фоном 7×7, что согласуется с физикой (раздел «почему горение видно из космоса»).

**Модуль BS.** Финальная конфигурация — пороговая модель из раздела 3 (IoU_burn 0.434,
mIoU_sev 0.462; sev1 0.228 / sev2 0.479 / sev3 0.679). U-Net по 42 каналам (S2 до/после,
NBR/dNBR/dNDVI, S1 VV/VH с разностями, рельеф, покров one-hot, флаги SCL; 1.9 M параметров)
написан и подготовлен (кэш признаков собран), но обучить в срок хакатона не успели —
честно фиксируем как ближайший шаг с наибольшим ожидаемым приростом.

**Итог через формат ответа.** `scripts/oof_submission.py` собирает OOF-предсказания всех
644 train-чипов в submission.csv (1 092 строки), файл проходит валидатор, декодируется
и оценивается; результат совпадает с прямым счётом по маскам (проверка конвейера):

| F1_af | IoU_burn | mIoU_sev | **Score (OOF)** |
|---|---|---|---|
| 0.953 | 0.434 | 0.462 | **0.624** |

**Найденная и исправленная утечка**: группы фолдов сначала строились через `hash()`,
рандомизируемый между запусками Python — фолды «плыли» и порог прыгал (0.36 vs 0.20).
Группировка переведена на строку даты; все опубликованные числа получены после исправления.

## 5. Инженерные и предметные решения

- **Дисбаланс классов (0.035 % позитивов)** — фильтр кандидатов до классификатора; контроль
  через микро-усреднённый F1, устойчивый к малой доле позитивов.
- **Облачность и тени** — жёсткое правило по SCL (nodata/тень/высокое облако → класс 0);
  устойчивость инференса: сбойный чип получает пустую маску, а не роняет весь сабмит.
- **Техногенные и отражающие объекты** — контекстные признаки (перегрев относительно
  локального фона в трёх масштабах) + тип покрова; проверено, что повторяемость детекций
  на train не работает (наблюдение 4) — решение принято по данным, а не по догме.
- **Тип покрова и рельеф** — пороги степени калиброваны отдельно для леса/травы/пашни/поймы
  (наблюдение 5); DEM и покров — признаки AF-модели.
- **Радиолокация (Sentinel-1)** — VV/VH и их разности включены в каналы U-Net; в финальной
  пороговой модели не используются — по нашим замерам спекл-шум без пространственной
  модели контур не улучшает.
- **Фенология «до/после»** — главный источник ложных контуров (убранные поля спектрально
  похожи на гарь, наблюдение 6); частично снимается порогами по покрову и минимальной
  компонентой, полностью — только пространственной моделью.
- **День/ночь** — контроль качества по подвыборкам и под смесь теста (наблюдение 3).

**Информационно-аналитический сервис** (`service/`, критерии Раздела 4): оффлайн-ingest
конвертирует маски (эталонные или предсказанные, из RLE) в геокаталог GeoPackage — термоточки
как центры пикселей VIIRS, контуры гарей полигонизацией маски по классам; геопривязка
из meta.csv (UTM 37N/38N). FastAPI держит каталог в памяти (9 725 термоточек, 99 239
контуров) и отвечает на пространственно-временной запрос за миллисекунды; REST API +
Leaflet-карта, выгрузки GeoJSON/Shapefile/JSON/CSV. Ключевое предметное решение — **все
площади считаются в родной UTM-зоне чипа** (пиксель = ровно 0.04 га), а не в градусах;
справка считает площадь пересечения контуров с полигоном запроса. Воспроизводимость чисел
проверена попиксельно: для крупнейшего пожара набора (FE12837) справка сервиса даёт
5 877.88 га = `burn_area_ha` из meta.csv, по степеням — точно `sev*_px × 0.04`.

Сервис на предсказаниях моделей (тот же код, второй каталог) на FE12837: контур и тяжёлые
степени воспроизводятся хорошо (итог 5 291 га против 5 878; средняя 3 355 vs 3 221, сильная
1 876 vs 1 984), слабая степень теряется (60 vs 673 га) — в полном согласии с IoU_sev1 = 0.228.

## 6. Итоговое решение и почему именно оно

AF — LightGBM на кандидатах с контекстными признаками и слабой исторической разметкой NOAA;
BS — калиброванные по покрову пороги dNBR с медианной фильтрацией
и отсевом мелких компонент (лучшее из обученного к дедлайну; степень внутри контура —
доказанно пороговая задача, наблюдение 5). Инференс детерминирован, тест обрабатывается
за ~9 с на CPU. Сервис — тонкий слой над геокаталогом, что делает запросы мгновенными
и разворачивание тривиальным (uv или Docker).

## 7. Выводы, типы остающихся ошибок, план развития

**Основной вклад в качество**: контекстные признаки AF (ночные пожары: F1 0.53 → 0.96);
калибровка порогов по покрову; честная CV с группировкой (после исправления утечки).

**Типы остающихся ошибок**: (1) слабая степень поражения — IoU 0.228, теряется на пашне,
где диапазоны dNBR классов 0 и 1 перекрываются; (2) ложные контуры на убранных/вспаханных
полях вдали от огня; (3) контур гари в целом (IoU_burn 0.434) — главный резерв метрики;
(4) риск сдвига на тест из-за большей облачности (наблюдение 8).

**План развития**: дообучить подготовленный U-Net контура (входы и кэш готовы) с выбором
«сеть vs правило» по CV; использовать S1-разности внутри сети; для сервиса — автозагрузка
свежих сцен из Copernicus/GEE (интерфейс ingest уже совместим) и переключатель
«эталон/модель» в UI.

## 8. Воспроизводимость

Seed 42 везде; фолды детерминированы (AF — дата съёмки, BS — чип); окружения зафиксированы
(`models/requirements-af.txt`, `service/uv.lock` + `.python-version`, Dockerfile для сервиса);
команды инференса, обучения и запуска сервиса — в корневом README.md; повторный прогон
`reports/af_augmented_best.json` фиксирует AF OOF и SHA-256 веса, повторный ingest — числа
справки сервиса. Для обучения AF использованы открытые исторические NOAA VIIRS SDR/AF EDR
только за зимние даты и вне тестового региона. Валидация содержит только данные
организаторов; география и даты теста не восстанавливались. Полный реестр источников,
лицензий и ограничений находится в `models/configs/af_external_data.json`.
